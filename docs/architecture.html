One notebook, multiple sources

Pass a dataset ID or a run group and a stable batch ID. Fabric uses the registered metadata to decide what to extract.

01 · Resolve

Workspace settings

vl_ingestion binds the environment, target Lakehouse, Landing root, and Key Vault reference.

02 · Plan

Job and checkpoint

nb_land reads the dataset and connection rows, then freezes a range or file list when the mode requires it.

03 · Extract

Connector to OneLake

REST, RaaS, JDBC, or ADLS writes into a unique attempt folder. Files coexist even when an attempt fails.

04 · Publish

Manifest and ledger

After the payload and manifest are written, a Delta success event publishes the batch and its next checkpoint.

Landing is the handoff. Bronze consumers read the manifest paths from successful ledger events. Silver and Gold can then apply data quality checks, deduplication, and business rules separately.

What changes for each client?

Workspace

vl_ingestion

Lakehouse and workspace IDs, client code, environment, Landing root, and Key Vault URL.

Connection

ops.connection

One row per connection and environment. Holds the adapter, endpoint or storage root, and secret names.

Dataset

ops.dataset

One row per dataset. Holds the connection ID, load mode, run group, and extraction options.

Two jobs fail. What gets retried?

This simulation uses ten jobs in one run group. Jobs 04 and 09 fail after their plans are saved. Reuse the same group and batch ID, or pass a single failed dataset ID.

A failed attempt can leave files in its own folder. The retry writes to a fresh folder and reuses the frozen bounds or file list. Its checkpoint moves when a success event is committed.

From Git to a first client run

  1. Create a schema-enabled Lakehouse and vl_ingestion in DEV. Set up the runtime identity and source access.
  2. Import and run nb_bootstrap to create the Delta tables and optionally seed disabled examples.
  3. Configure one connection and enable one dataset. Run nb_land with a stable test batch ID.
  4. Check the manifest in OneLake and the success event in ops.landing_event. Run the same batch again and expect already_succeeded.
